# pve-meta — adversarial review, pass 2 (adjudicated)

## 1. Verdict

Pass 1 found a design that was coherent and an implementation that did not enforce it: 6 critical, 10 high, 13 medium, 1 low, with the write-authorization boundary computed from side effects, an extension seam that could kill pvedaemon, unlocked cluster-shared writes, and roughly a fifth of `pve-meta-core` unreachable. That rework landed: 26 of the 30 findings are fixed and independently verified (live on node1 where behaviour was observable), 4 are partial, none regressed, and the whole class of "dead subsystem advertised as live" is gone. Pass 2 is a different shape — 2 critical, 4 high, 7 medium, 18 low, and no finding is a straight reopening of a pass-1 defect. What remains clusters in two places. First, the security boundary that F1/F2 rebuilt is now correct about *paths* but blind about *actors*: any principal holding a broad `rw` scope (an empty prefix is legal and tested) can write `scopes` itself, which DESIGN §2 forbids in as many words — a full privilege-escalation path reproduced against the unmodified crate. Second, the "validate at write, read leniently" rule that F7 established for `scopes` was implemented one layer too high: `store.read` still runs whole-document `model::lint` on every read *and* on the pre-existing content inside `put_raw`, so a single out-of-band invalid key anywhere in `datacenter.yaml` 400s every guest operation cluster-wide for everyone including full-ACL admins, and blocks the admin's own repair write — the exact outage F7 was raised for, now reachable through any lint rule rather than only a malformed scope entry. The rest is residue: three of the four partial fixes (F7b, F11, F20) left the second half of their own remit undone, the F16/F18 rewrites of `pve-ext-patch` introduced a `--root` isolation leak and a filename-derived claim identity, and DESIGN §3's API table now contradicts DESIGN §8 and the code on three rows — "one invariant, two owners", pass 1's own theme, transplanted from the code into the spec.

## 3. Prioritized fix list (confirmed)

### G1 — The security boundary is correct about paths and blind about actors and about failure (P1–P4, fix together)

**P1 · critical · `crates/pve-meta-core/src/api.rs:460` · S**
`validate_scopes_if_touched(doc_id, planned, touched)` takes no `grants` at all: it checks only that a write touching `scopes` leaves it structurally parseable. `authorize_view_write` requires just `grants.can_write(view_path)`, and `Path::root()` (an empty-prefix scope, explicitly accepted — see `parse_scopes_allows_root_prefix`, scopes.rs:487) covers every non-root path including `scopes`. The `view_path.is_root()` guard does not fire, because `?view=scopes.<authid>` is not a root view. So a `full_write:false` principal holding one broad `rw` scope can grant itself or anyone else arbitrary prefixes — privilege escalation inside the module whose own doc comment calls it "the project's security boundary", contradicting DESIGN §2 verbatim ("any write touching `scopes` is refused for scope-granted principals"). Reproduced twice, independently, against the unmodified crate: `put_document(… view="scopes.evil@pve", grants={full_write:false, scopes:[{prefix:"", mode:"rw"}]})` returns `Ok` with `touched:[scopes.evil@pve]` and writes durably.
*Fix:* thread `grants: &Grants` into `validate_scopes_if_touched` and its one call site (`plan_write`, api.rs:451); after confirming the write touches `scopes` and before `parse_scopes`, `if !grants.full_write { return Err(forbidden(grants, &scopes_path)); }`. Regression tests: `full_write:false` with a root-prefix `rw` scope and with a `scopes`-prefix `rw` scope are both 403 on PUT and DELETE; `full_write:true` is still allowed regardless of scope coverage. Decide the empty-prefix scope question at the same time (LOW #1 below) — P1 closes the `scopes` hole, not the "empty prefix ≈ `VM.Config.Options` on every guest" hole.

**P2 · critical · `crates/pve-meta-core/src/store.rs:214` (and `:297`) · S**
`read_document` parses every document with `format::parse`, which runs strict whole-tree `model::lint`; `put_raw` re-parses the *existing* on-disk content the same way purely to compute a diff. Since every API write is already lint-gated, the only source of invalid content is out-of-band (a hand-edited `/etc/pve/meta/*.yaml`, a restored backup, pmxcfs replication) — and one bad key or `null` anywhere then makes `store.read` throw `Error::Lint` → 400. `api::grants` reads `DocId::Datacenter` on every call, and Perl's `_scopes_for` runs on every guest GET/PUT/DELETE, `/meta/guests` and `/meta/access`, so one typo in `datacenter.yaml` denies every guest operation cluster-wide to every principal. F7's lenient `scopes_for` never runs — `store.read` fails first. Worse than the F7 original: a full-ACL admin cannot GET the document to see what to fix, and cannot repair it with a targeted write, because `put_raw` re-parses the old content strictly before diffing. Reproduced independently by both verifiers.
*Fix:* `read_document` (`:214`) and `put_raw`'s parse of `old_raw` (`:297`) use the already-`pub(crate)` `format::parse_raw`; leave `put_raw`'s parse of the *new* `normalized` text (`:304`) on strict `format::parse` — that is the real write-time gate. Regression tests: a document with an out-of-band invalid key is still readable, and a full-ACL admin can repair it via a root-level `replace`.

**P3 · high · `crates/pve-meta-core/src/scopes.rs:238` (and `:173`) · S** *(F7 residue)*
F7(b) made *entries* lenient but left the container check strict: `scopes` present and not an object → `Error::InvalidScopes` → 400 on every guest endpoint for every caller, admins included. A single indentation slip in raw YAML turns the map into a string. DESIGN §8's promise is broader than the fix delivered ("read leniently … never denies service to anyone else"). Pinned today by `scopes_for_rejects_a_non_map_scopes_key`. Mitigation confirmed: `/meta/access?dc=1` and `get_datacenter` never call `_scopes_for`, so the Datacenter tab still loads to repair it.
*Fix:* in `scopes_for`, a non-object `scopes` → `tracing::warn!` + `Ok(Vec::new())`. Keep `parse_scopes` strict (it is the write gate). Replace the pinning test with its negation plus an assertion that `parse_scopes` on the same value still errors. Same fix philosophy as P2; ship them together.

**P4 · high · `crates/pve-meta-core/src/view.rs:342` · S** *(F11 residue)*
F11 fixed `p__`; the bare `__` map comment now gets three answers from three layers. `scopes::covers` (scopes.rs:92) deliberately excludes it, so `can_read("__")`/`can_write("__")` are false for a scope holder — but `filter_map` emits `__` into the union read whenever anything else in that map survived. Verified live with the zero-ACL scoped token: the document-root note `__: top level note - secret-ish` is returned in the view-less read, while `GET ?view=__` and `PUT ?view=__` both 403. That is a genuine read-side disclosure — the root `__` documents the whole document, including parts the principal has no grant for — and one verifier raised it from medium on exactly that ground.
*Fix:* pick one rule and enforce it in both layers. (a) `filter_map` emits a map's bare `__` only when that map itself is readable by the grant, `covers` unchanged; or (b) `covers` aliases a trailing bare `__` to its parent path, and `filter_map` consults it. State the choice in DESIGN §1/§8 next to the existing `p__` sentence, and add the paired regression test: `filter` must never emit a `__` the same grant's `can_read` refuses. Test `filter_bare_map_comment_travels_only_when_something_included` currently pins the bug and must be replaced.

### G2 — Lifecycle: orphan documents are now unremovable (P5)

**P5 · high · `perl/PVE/API2/Ext/Meta.pm:601` · M** *(F20 residue)*
F20's guard closed unbounded creation and simultaneously closed the only API path that removes a document whose guest is gone; the orphan sweep the fix listed (`REVIEW-2026-09-07.md:103`) was never written (`grep -rni orphan` hits only an unrelated snapshot test). Orphans are reachable in practice — a guest destroyed while its node is down, a restore onto a different vmid, a manual `rm` of the config. The resulting document is readable, invisible to `GET /meta/guests`, counted by `GET /meta/version`, replicated by pmxcfs against its size budget, silently inherited by a future guest at that vmid, and removable only by root with `rm`. Reproduced live twice: `DELETE /meta/guests/999000` → 404, file still present. Undocumented — DESIGN §8 states the create guard and is silent on cleanup.
*Fix:* keep the unconditional guard in `put_guest`; in `delete_guest` 404 only when the vmid is absent from the vmlist **and** no document exists (`PVE::RS::Meta::has_document` already exists, `crates/pve-meta-perl/src/lib.rs:214`). Add the promised sweep (`GET /meta/guests?orphans=1`, or a timer-driven `pve-meta-sweep`) and record both decisions in DESIGN §8 next to the create guard.

### G3 — pve-ext-patch: the F16/F18 rewrites introduced two identity/isolation defects (P6, P7)

**P6 · high · `pve-ext/bin/pve-ext-patch:314` · S**
`FAILURE_MARKER_DIR="${ROOT_DIR}/run/pve-ext-patch"` is the file's only top-level statement derived from `ROOT_DIR`; it evaluates during the initial pass with `ROOT_DIR` still `""` (line 79), because `--root` is parsed inside `main`, invoked on the last line (896). Every other root-derived path (`manifest_dir`, `real_path_for`, `diverted_path_for`, `set_dpkg_root_args`) is a function and re-reads `$ROOT_DIR` at call time. So an apply failure under `--root` — the CI/dev workflow the tool's own `--help` advertises, and which explicitly permits running unprivileged — writes a failure record to the **real** `/run/pve-ext-patch/failed` and the real syslog. Reproduced live on node1: the marker landed on the host, `/tmp/pve-ext-patch-test/run/pve-ext-patch` was never created.
*Fix:* `failure_marker_dir() { echo "${ROOT_DIR}/run/pve-ext-patch"; }`, called from `record_failure` at invocation time. Suppress or clearly tag the `logger` call when `-n "$ROOT_DIR"`.

**P7 · medium · `Makefile:81` + `pve-ext/bin/pve-ext-patch:534`,`:605`,`:433-437` · S**
The F18 claim marker's identity is `basename "$manifest" .toml`. The manifest is `patches/lifecycle.toml` in the checkout and `pve-meta-lifecycle.toml` when installed, and `resolve_manifest` returns a literal path argument unnormalized — so a checkout-run `apply patches/lifecycle.toml` (a workflow the tool header advertises) writes the claim `lifecycle`, after which every packaged `apply pve-meta-lifecycle` refuses all seven files, including the dpkg-trigger re-apply after a `qemu-server`/`pve-container` upgrade — precisely the F16 scenario. `postinst` swallows it. `scripts/watch-pve/check.sh:171` already works around this exact trap at one call site, evidence it is known and only locally patched. Compounding: the claim-mismatch branch is the one failure exit in `apply_one` that calls neither `record_failure` nor `restore_on_failure`, so it leaves no `/run/pve-ext-patch/failed` entry at all.
*Fix:* add a top-level `name = "pve-meta-lifecycle"` key to the manifest, parse it, use it as `mname` with basename as fallback. Interim: rename `patches/lifecycle.toml` → `patches/pve-meta-lifecycle.toml` and update `Makefile:81`, `docs/DISTRIBUTION.md`, `check.sh:37,171`. Independently, make the mismatch branch call `record_failure`.

### G4 — Editor: one un-invalidated channel, one O(N) round trip (P8, P10)

**P8 · medium · `ui/src/editor.rs:712` · S**
`Msg::Reload` clears `draft`/`write_error` and bumps `generation`, but never touches `self.requests`: no epoch bump, no `invalidate()`. `accepts()` checks only epoch/doc/view/per-channel seq, so an `Apply`/`Diff`/`Digest` request issued before the Reload still passes and its late answer is applied over the freshly reloaded document — e.g. a 409 arriving after the reload sets `stale` and `write_error`, rendered unconditionally, on a document with no unapplied edits whose own Reload button is then a no-op. `RequestTracker::invalidate()` exists, is unit-tested, has a doc comment describing exactly this case, and has zero production callers: the wiring was written in `request.rs` and never connected.
*Fix:* `self.requests.invalidate()` in `Msg::Reload` before `send_reload()`. This also gives `invalidate()` its first caller (see LOW: three dead tracker methods).

**P10 · medium · `ui/src/editor.rs:501` · M**
On first load for a guest, `load()` calls `api::guests()` solely to find that guest's `name` for the header line — and `self.guest` is reset on every doc change. `GET /meta/guests` is O(N) by construction: Perl walks the whole vmlist, does a per-vmid ACL check plus one cluster-wide `get_guest_config_properties` broadcast, and `api::list_guests` then calls `read_or_empty` (file read + YAML parse) for every guest whose grants are non-empty — which, because scopes are not per-vmid, is *every* guest for any scope holder. Confirmed live: all four vmids returned, including two with no document on disk. `api::guests()` has no other caller in the UI.
*Fix:* return the identity with the document — add `name` (and `node`) to `ApiViewDocument`, populated in `get_guest` from the vmlist row plus a single-vmid `get_guest_config_properties`, gated on `VM.Audit` exactly as `list_guests` gates them; then drop the `need_guest` branch, the `GuestEntry` import and the surrounding bookkeeping. Note `list_guests`' `read_or_empty` is largely forced by DESIGN §3's documented `keys` field, so "skip the read" is not free — a `vmid` filter on the endpoint is the cheaper half.

### G5 — Scopes live inside the path-addressed document, and inherit its charset (P9)

**P9 · medium · `crates/pve-meta-core/src/model.rs:25` · L (or S as documentation)**
`scopes`' keys are PVE authids but are validated as document keys: `is_valid_key` = `is_valid_segment` = `^[A-Za-z0-9_@!-]+$`. `@` and `!` were added for authids; `.` cannot be, because it is the path separator. PVE usernames and realm ids both permit dots (`/usr/share/perl5/PVE/Auth/Plugin.pm:34-35`), so `john.doe@pve`, `svc@ldap.corp` and every LDAP/AD-synced `first.last@…` can never be granted a scope: the write 400s at lint (verified live, `dry_run=1`) and even a hand-written entry is unaddressable (`?view=scopes/john.doe@pve` → `invalid path`). This is the structural cost of putting ACL config inside the free-form dot-addressed document; DESIGN §2 says only "keyed by authid" and flags no limitation, though it does flag others ("no per-vmid scoping in this revision").
*Fix:* validate `scopes`' own keys with a PVE-authid rule rather than `is_valid_key`, and address a single entry via a dedicated `authid` parameter (or an escaped segment) instead of `?view=scopes.<authid>`; `check_write` then treats `scopes` as an opaque leaf for touched-path purposes. If that is too much for 1.0, state the limitation in DESIGN §2 and make the rejection say *why* rather than emitting a generic key lint.

### G6 — Docs and packaging process (P11, P12, P13)

**P11 · medium · `docs/DESIGN.md:60`,`:64`,`:65` + `README.md:70`,`:71` · S**

One verifier rated the README row high, the other medium; adjudicated medium as a group.

Tighten README's PUT 403 wording to cover the view-level refusal and the root-view rule. Folds in two LOW items (README:70, DESIGN:66).

## 4. Refuted findings

**Guest list leaks cluster vmid/type inventory to any single-scope token** (`Meta.pm:476`, medium) — technically reproduced, but it is specified behaviour. DESIGN §8 states `GET /meta/guests` "lists only guests the caller can read something of; `name` and `node` are included only with `VM.Audit`", and §2 makes the premise binding: "a scope grants that principal the prefix on every guest document (no per-vmid scoping in this revision)" — so a scope holder legitimately can read something of every guest. The gated-field list deliberately names `name`/`node` and not `vmid`/`type`; the code says so in three places (`api.rs:301-303`, `Meta.pm:432-435`, the Rust doc comment). The finding's own fix text concedes §8 "currently only speaks to name/node". Contradicts a documented decision rather than identifying a defect. If the decision is wrong, revisit it in §2/§8, not as a bug.

**The version poll re-hashes the entire store every 5 s** (`store.rs:444`, medium) — accurate as description, but it is the adopted F25 fix, not a slip. DESIGN §3 specifies the endpoint with no parameters and store-wide scope; §8 states "Digest and version are computed from file content on every call (no mtime cache)". The whole-store scope predates F25 (the removed cache sat on top of an already store-wide scan), and every layer documents the tradeoff deliberately — `store.rs`'s doc comment explaining why a cache would be unsound, `editor.rs:52-53`'s comment accepting the one-document re-read as the known cost, `Meta.pm:350`. Both suggested remedies (add an `id` param; reintroduce an mtime cache) reopen decisions §3 and §8 settled. Performance concern, not a defect; carried to §6 instead.

**`ext_path` accepted unvalidated** (`pve-ext/perl/PVE/API2/Ext.pm:154`, medium) — the mechanism is real and was fully traced (a multi-segment `nodes/backup` registers into the same tree but is unreachable, because `map_path_to_methods` follows core's `SUBCLASS` jump at the first segment, while `/ext/modules` still reports it mounted). Refuted on materiality: the only extension in the tree is `Meta.pm`, whose `ext_path` is the literal `'meta'`, so no untrusted input reaches the seam today; installing a `PVE::API2::Ext::*` module already requires root, the same trust boundary as everything pvedaemon loads, so the seam is a DX nicety, not a security control; and DESIGN §8's binding decision for this seam — the record of a prior dedicated review of this exact file — enumerates crash-safety and collision-skipping only. Worth a shape check when a second extension author appears; not a 1.0 blocker.

**The shipped page manifest requires VM.Audit, so the tab is unreachable for scope-only principals** (`pages/pve-meta.json:7`, medium) — the reachability gap is real and was reproduced end-to-end, but two things sink it. The manifest content is quoted verbatim in DESIGN.md:85-98 and `pve-ext/README.md:80-90`, which also states `requires` is "a UX convenience only … not the access control" — so "nothing in DESIGN or README says so" is factually wrong. More decisively, the proposed fix does not fix the described scenario: a zero-ACL principal never appears to have the guest in PVE's resource tree at all (confirmed live: `/cluster/resources?type=vm` → `[]`), so `PVE.lxc.Config` is never constructed and dropping `requires.vms` changes nothing. The real blocker is PVE core's ACL-gated tree, outside this project. At most a documentation nit; the standalone iframe URL in §6 is the documented path for such principals.

## 6. Before 1.0

Three of the four partial fixes are the same failure: the remit was split into halves and only the first half shipped, with no marker left behind. F7 made entries lenient and left the container strict (P3); F11 aliased `p__` and left the bare `__` (P4); F20 added the create guard and never wrote the sweep, while removing the only path that could have compensated (P5). Each is small. The pattern is not: a fix whose second half is silently dropped reads as closed in every subsequent audit. Close all three, and put the choice each one makes into DESIGN §8 as a sentence, because in all three cases the reason the residue survived is that §8 recorded only the half that shipped.

The second thing to settle is what `scopes` actually is. Today it is a subtree of a free-form, dot-addressed, whole-document-linted YAML file, and every consequence of that is now visible: an actor check is missing from the one write path that matters (P1); the document's key charset silently excludes a large class of legitimate PVE authids (P9); an empty prefix is a legal scope that means "everything" (LOW); and a lint failure anywhere else in the same file takes the ACL lookup down with it (P2). Those are four symptoms of one decision. Either commit to it — with the actor gate, an authid-shaped key rule, an explicit ruling on the empty prefix, and a lenient reader — or move `scopes` out of the document before 1.0 fixes the shape by inertia.

Third, `pve-ext-patch` now has two identities that are not identities: the failure marker's root (P6) and the manifest's claim name (P7). Both were introduced by the F16/F18 rewrites, both are one-line-ish, and both only fail in the upgrade and CI paths that the rewrites existed to protect. The `--root` contract in particular is advertised in the tool's own help text; it should hold for every path the tool touches, including the ones it writes on failure.

Finally, accepted costs that should be written down rather than re-discovered next pass: the version poll is O(store) per open tab by design (§8 already says why, and the editor comment already accepts it) — say so in §3 too, so it stops reading as an oversight; `ext_path` takes arbitrary shape from a third-party module and will silently mis-mount a multi-segment path (fine while one extension exists, needs a rule before a second); `import_from_backup` still converts a legacy non-YAML blob while the store is YAML-only (one sentence); and `list_guests` reads and parses every guest document for a scope holder because scopes are not per-vmid (P10 covers the UI half; the endpoint's own cost is the design's, not a bug). None of these blocks 1.0. All four will be re-filed as findings if they stay undocumented.
