# pve-meta — adversarial review, revision 5 (final adjudication)

## 1. Verdict

Revision 5's simplification held on the core: the machinery that produced pass 4's top findings is gone rather than patched — `lint_at`/`lint_relaxed*`/`WriteGate` (Q1's regression), the reserved `scopes` key and its four addressing surfaces (Q7), `may_name` redaction, the orphan concept across all five surfaces (Q3, Q9), the `keys` wire field (Q11), the JSON-string crossings, and the destroy/clone/backup hooks with their six diffs; the pwt editor's rewrite to a tree took Q2 and Q4 with it (`access_for` no longer exists). Pass 4 was 0 critical / 1 high / 3 medium / 7 low; this pass is 0 critical / 3 high / 4 medium (one reinstated over a refutation) / 7 low, and — for the first time in four rounds — **the highest-severity finding was not introduced by the previous pass's fix**: the three highs are pre-existing code the simplification never touched (a store-level TOCTOU that predates rev 5, and two defects in the hand-written ExtJS YAML/tree layer, which rev 5 added rather than simplified). What the simplification broke is confined to prose and packaging drift — six of the seven lows are stale section numbers and file counts left behind by the renumbering — and it did not close the two pass-4 lows that live below the deleted layer: `version()`/`digest_of` are still uncapped (Q5, verified still open at store.rs:615-646), and the repair path is still keyed on `parse_error` alone (Q6, api.rs:480, recheck). Two of the submitted findings were already fixed in the working tree mid-review and are dropped as stale, which is itself a symptom: this tree is moving under the review.

## 2. Prioritized fix list (confirmed)

Ordered by priority. Group B is contingent on the keep-one decision (§5) — do not spend effort there before it is made.

### Group A · store / API core (implementation-independent, fix regardless)

**S1 · high · `crates/pve-meta-core/src/store.rs:319` · effort S**
*Defect.* `read()`/`read_document()` (272, 278), `version()` (622, 625, 626) and `delete()` (462) all check existence then act on a separate syscall, propagating a racing `io::ErrorKind::NotFound` as `Error::Io` → HTTP 500. `read_or_empty`/`read_tolerant` catch only `NotFound`, so the 500 escapes; because `list_guests` calls `read_tolerant` with `?` in its loop, one vanished file 500s the whole listing. Reads run unlocked, writes hold `pve-meta-<id>`, GC holds `pve-meta-gc` — three disjoint domains, so no reader is ever excluded. Live-reproduced: 3/500 GETs, 51/800 list calls, 540/4000 `version()` polls, 25/3000 double-GC runs. The correct idiom already exists two functions away in `digest_of` (331) and `check_precondition` (367).
*Fix.* Match `ErrorKind::NotFound` in `read_document` → `Error::NotFound(id)`; treat it as success in `delete()` (documented idempotent); `continue` past it per entry in `version()`. Re-check `delete_document`'s own locate-then-delete (api.rs:720) after.

**S2 · medium · `crates/pve-meta-core/src/api.rs:760` · effort M**
*Defect.* `gc()` purges every stored vmid absent from a caller-supplied `live` snapshot, with no per-vmid lock and no re-validation before `store.purge()`. Writes serialize under `cfs_lock_domain("pve-meta-$id")`, GC under `cfs_lock_domain('pve-meta-gc')` — disjoint. A destroy → recreate-at-same-vmid → PUT landing inside a GC pass whose vmlist read predates it has its fresh document silently deleted, with the PUT already 200. Both verifiers reproduced it independently in-crate (`live=[100]`, `put_raw(999500)`, `gc()` → `removed==1`, subsequent read NotFound). Only silent server-side data loss in this pass.
*Fix.* Acquire `cfs_lock_domain("pve-meta-$vmid")` per stale vmid in `libexec/gc` and re-check liveness against a fresh vmlist inside that lock before purging, or thread a per-vmid liveness callback into `api::gc`.

### Group B · ExtJS UI (`ui-extjs/pve-meta-tree.js`)

**S3 · high · `:990` · effort S** *(reported critical; adjudicated **high** — both verifiers independently downgraded, and I concur: blast radius is one browser tab's `Object` builtin plus one row, cleared on reload, with the on-disk document verified untouched)*
*Defect.* `entry()` does `parent.children[key] = parent.children[key] || {...}` against a `{}` literal, so a document key matching a truthy `Object.prototype` member (`constructor`, `hasOwnProperty`, `toString`, `valueOf`, …) short-circuits: `entry()` returns the page's global `Object`, and `addData()` writes `.present/.kind/.value` onto it. `isComment()` only filters keys ending `__`; `key_lint` (model.rs:80) is `^[A-Za-z0-9_@!-]+$` with no reserved list, and DESIGN §2 says no key is reserved — so the server accepts `constructor` (live-verified end to end). The row's `path` is then `undefined`, so its next edit/remove issues `?view=undefined`.
*Fix.* `Object.create(null)` (or a `Map`) for every map whose keys are document keys: `entry()`'s returned node, `buildTree()`'s root, `toNodes()`'s traversal, `addGrammar()`'s walk.

**S4 · high · `:101` · effort S**
*Defect.* `yamlScalar()`'s `needsQuotes` only flags a colon that is leading or followed by whitespace, so the key `a:b` is emitted unquoted as `a:b: v`; `yamlBlock()`'s matcher (`:241`) cannot parse it back, and — because it is the first line of a nested block — falls through the bare-scalar escape hatch instead of throwing, promoting the next sibling out of its parent. Verified against the unmodified shipped file: `{traefik:{'a:b':'v',host:'x'}}` round-trips to `{"traefik":"a:b: v","host":"x"}`, no exception. Contradicts the module's own guarantee (lines 93-99) that ambiguous input "throws rather than being silently mangled". One verifier established the corruption needs only a single YAML→JSON toggle plus Apply (`mode=replace`), not the double round trip in the original write-up; `showDiff()` re-parses through the same parser, so the confirmation diff can mask it.
*Fix.* Quote on any colon anywhere. Make `yamlBlock()`'s unparsable-first-line branch throw unconditionally instead of falling back to a bare scalar. Add a mid-string-colon key fixture to `testing/smoke.js` (its only colon fixture is in a *value*).

**S5 · medium · `:918` · effort S**
*Defect.* `poll()` checks `me.editing || me.textWindow` only before issuing `GET /meta/version`; the success callback calls `me.reload()` → `setRootNode()` unconditionally on token change, and `reload()` guards only `rendered`/`isDestroyed`. An edit started after the request went out is torn down mid-flight. `testing/headless-flows-check.js:258` only exercises the synchronous guard, so the suite cannot catch it.
*Fix.* Re-check `me.isDestroyed || me.editing || me.textWindow` inside the callback before `reload()` (let the next 5 s tick pick the token up); optionally also inside `reload()`.

**S6 · medium · `:861` · effort M · VERIFICATION INCOMPLETE** *(reinstated over a refutation — see §3)*
*Defect.* `loadTags()` resolves `selector:{tag:t}` scopes from `GET /meta/guests`'s `tags`, which the server returns only to a caller with VM.Audit (DESIGN §5, api.rs:394-433). A scope-only principal gets `tags:null` → `me.tags=[]` → `applicableScopes()` never matches its own tag-selector scope → `ownerFor()` returns `''` and `addGrammar()` adds no declared rows, for exactly the rows it is scoped to write. `editableFor()` reads `/meta/access`'s server-resolved scopes, so writes are unaffected: display-only, but DESIGN §8 promises both.
*Incomplete.* Neither verifier reproduced it in the lab's default state: the packaged `example-traefik.yaml` carries an unconditional `all:true` scope on the same `traefik` prefix, and `applicableScopes()` iterates *all* registrations, so it masks the defect wherever a second registration covers the prefix. Both confirmed it in isolation (a non-colliding prefix; the masking registration removed from the input). Before fixing, confirm on a deployment with a single tag-selector registration.
*Fix.* Resolve selectors server-side — return the applicable registrations/grammar in `/meta/access` (which already resolves scopes without VM.Audit) rather than re-deriving them client-side from a VM.Audit-gated field.

### Group C · pwt UI

**S7 · medium · `ui/src/editor.rs:296` · effort S**
*Defect.* `may_add()` returns `self.access.write || any scope is rw` and never consults the selection, while `add_dialog()` (:548) derives its target from the selected node (map's path, else the leaf's parent, else root). A scoped principal with rw on one prefix keeps an enabled Add button while an unwritable row — or nothing — is selected; the dialog opens targeting it and fails at submit. Edit/Remove and `text_dialog()` already gate on the target's `writable`. DESIGN §8: "Editability is per row from `/meta/access`". No security consequence; the server remains the arbiter.
*Fix.* Compute the same parent `add_dialog()` will use and gate on `access.may_write(&parent) || (parent.is_empty() && access.write)`, reusing the existing `Access::may_write`.

## 3. Overruled refutations

**Overruled — reinstated as S6:** *"A principal with only a tag-selector scope can never see its own Owner label or grammar rows."* The refutation disproves the cited evidence, not the defect: it shows the lab repro was masked by the packaged `example-traefik.yaml`'s `all:true` scope on the same prefix, and then states outright that on a non-colliding prefix `ownerFor()` does return `''` "confirming the code defect is real in principle". The second verifier reproduced the same thing by removing the masking registration from otherwise-live data. A defect that is invisible only because a shipped demo registration happens to cover the same prefix is a defect. Reinstated at medium with the verification qualified.

**Upheld:** *CI never installs npm* — `build.yml:32` now installs `nodejs npm`; fixed in-tree mid-review. *`debian/control:31` advertises deleted hooks* — already corrected in-tree (see above). *`api::gc` treats an empty vmid list as "every guest is gone"* — upheld as a deliberate, documented, tested contract (PERL-BINDINGS-SPEC "the cfs_update() and the empty-vmlist guard are not optional"; `api.rs:~1376` and `crates/pve-meta-perl/test/basic.pl:120` both assert it), with one caller that carries the guard. Note for 1.0, not a finding: this is the single most destructive operation in the system, guarded by one line of Perl at one call site, and S2 shows the GC path already has an unguarded edge. A three-line `if vmids.is_empty() { return Err(...) }` in `api::gc` with an explicit opt-out for the tests costs nothing and removes the footgun from every future caller.

## 5. UI verdict (input to the keep-one decision)

**pwt (`ui/`) carries fewer and less severe defects.** Count: ExtJS 2 high + 2 medium (S3, S4, S5, S6); pwt 1 medium (S7), and the two pass-4 pwt findings (Q2 stale access, Q4 undocumented fallback) died with the editor rewrite.

The gap is structural, not incidental. Three of the four ExtJS defects come from work the ExtJS implementation has to do itself and pwt does not:

- **YAML.** ExtJS hand-writes a dumper *and* a parser (S4) and re-parses through them on every mode toggle and diff. pwt asks the server for text (`format=yaml`, `api.rs:149`) and sends text back — the round trip is `serde_yaml` on both ends, and the class of bug S4 represents cannot exist there.
- **Untyped maps.** S3 exists because JS object literals double as hashmaps and document keys are attacker-chosen-ish by design ("no key is reserved"). Rust's `Map`/`HashMap` has no prototype chain; the whole class is absent from pwt.
- **Async discipline.** S5 is a guard checked before an in-flight request and not after. pwt's message-passing update loop makes the same mistake possible but does not invite it, and its equivalent path was the one already hardened in pass 3 (F4/F5).
- **Server-resolved vs client-re-derived state.** S6 is ExtJS re-deriving scope applicability from a permission-gated field. pwt reads the already-resolved `/meta/access`; S7 is the mirror-image mistake — pwt has the right data and fails to consult it for one button, which is a one-line fix against an existing helper.

Against that, ExtJS's advantages are real but orthogonal to defect count: native look, no wasm/trunk/Monaco toolchain (the `npm` CI breakage that was fixed mid-review was a pwt-build dependency), and no 1280-line file needs a Rust toolchain to patch. If ExtJS is kept, S3 and S4 are the price of admission and the hand-written YAML layer needs a round-trip property test, not just fixtures — S4 was live only because `smoke.js` has a colon in a value and never in a key. **Decision not made here.**

## 6. Before 1.0

Land S1 and S2 first: they are implementation-independent, they are the only findings that touch stored data or every caller, and both are small. S1 is a mechanical application of an idiom already in the file; S2 needs the per-vmid lock in `libexec/gc`, and while that file is open, add the belt-and-braces empty-vmlist guard inside `api::gc` (§3).

Then make the keep-one UI decision, and only then spend on Group B or C. Fixing S3-S6 in an implementation that is about to be deleted is the single largest avoidable cost left in this project.

Still open below the deleted layer, carried from pass 4 and re-verified against rev 5: **Q5** — `version()` (store.rs:615-646) and `digest_of` still read and SHA-256 every file uncapped, so the 5 s poll and every listing pay full cost; `MAX_READ_BYTES` (4 MiB) remains unreachable above pmxcfs's 1 MiB ceiling, so the `TooLarge` arms are dead code. **Q6** — needs a recheck, not a re-report: the repair path still keys on `parse_error.is_some()` (api.rs:480), so a file that *parses* to `null`, a scalar or an array (an empty or comment-only file being the likeliest out-of-band corruption) still appears to bypass it.

Two process items. First, every finding here should land with the regression test named in its fix; S4 and S5 in particular are live because the ExtJS suite tests the adjacent case (`colon in a value`, `editing already true`) rather than the failing one. Second, two of the six submitted CONFIRMED findings and both refuted non-UI findings were already fixed in the working tree by the time they were adjudicated. That is a review racing an active branch. Freeze the tree, or tag the revision under review, before pass 6.
