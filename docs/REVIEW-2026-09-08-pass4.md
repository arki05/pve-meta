# pve-meta — adversarial review, pass 4 (final, targeted, adjudicated)

## 1. Verdict

Pass 3 found a store that turned any out-of-band YAML typo into an unrepairable cluster-wide 400, a filter arm that handed a non-map document whole to a scope-only reader, and a packaging rollback that never rolled back: 1 critical, 4 high, 4 medium, 7 low. All nine numbered findings were shipped and independently re-verified; seven are fully fixed (R1, R2, R4, R5, R7, R8, R9) and two are partial (R3, R6), and five of the seven low-checklist items are closed. The critical is gone: parse failures now degrade per document, repair through a root replace or DELETE works live, and probing eighteen breakage shapes produced no content leak to a scoped reader. What is left is smaller but of the same species pass 3 named — **the highest-severity finding in this pass was again introduced by a pass-3 fix, the third consecutive round in which that happened**: R6's narrowed subtree lint anchors only at the view path's *last* segment, so a zero-ACL scoped token can plant a comment key holding an object and thereby deny the guest's own administrator every narrow write and merge until a whole-document replace. Pass 4 is 0 critical, 1 high, 3 medium, 7 low, and one medium (§3 `/meta/access` row) is only single-verified. The remaining mediums are the deferred half of R3 (client-side access staleness on scope revocation) and two documentation gaps that are the same "the fourth row was never updated" pattern R9 fixed one row over.

## 3. Prioritized fix list (confirmed)

### Q1 · high · `crates/pve-meta-core/src/api.rs:750` · S *(regression introduced by the R6 fix)*

**Defect.** R6 replaced `plan_write`'s whole-document `model::lint(planned)` with `model::lint_at(&subtree, view_path)` for any caller without `full_write`, and narrowed the store gate to `WriteGate::CallerLinted`. `model::lint_at` (model.rs:180) applies the two parent-anchored rules — the key rule and "a comment key's value must be a string" — to `view_path`'s **last** segment only. Every other segment is materialised blindly by `view::descend_creating` (view.rs:88) and checked nowhere: `view::replace`/`merge` lint only the payload (`lint_relaxed_at`/`lint_patch_at`, anchored at the prefix), and `WriteGate::CallerLinted` (store.rs:478) requires only "parses, and is a map". So `PUT ?view=<scope>.<name>__.<leaf>` makes a comment key hold an object. `Grants::check_write` permits it (`covers` is plain prefix containment) and `touched` reports a path genuinely inside the caller's scope. The stored document then fails `model::lint` — the gate every `full_write` caller still runs — so a low-privileged principal permanently disables the high-privileged principal's narrow writes and merges. This breaks the invariant the fix's own test `the_narrowed_lint_still_refuses_everything_inside_the_written_subtree` (api.rs:1783) states in its comment ("narrowing the *scope* of the lint may not narrow the *rules*") and SPEC.md:80; the test covers a comment key at the view root and inside the payload, never as an intermediate segment.

**Evidence.** Live on node1, `scoped@pve!t1` (zero PVE ACLs, `scopes: [{prefix: traefik, mode: rw}]`), guest 201: `PUT ?view=traefik.q__.r data=1` → 200 `touched:[{path:"traefik.q__.r",op:"set"}]`; file becomes `traefik:\n  host: a\n  q__:\n    r: 1\n`. Thereafter from `root@pam!traefik1` (full `VM.Config.Options`): `PUT ?view=other`, `mode=merge {"other":1}` and `PUT ?view=traefik.spec.host` all 400 with `traefik.q__: comment key value must be a string`; only a whole-document replace is accepted. Both verifiers reproduced it in-crate independently (`?view=p.__.x`, `?view=p.a__.b.c`, `?view=p.q__.r` accepted under `{prefix:"p",mode:"rw"}`), and both confirmed the identical call is refused at 67b3473, pre-R6-fix.

**Fix.** Anchor the narrow lint at every segment of `view_path`, not just the last: in `plan_write`, walk `view_path`'s proper ancestors root-down and apply `model::key_lint` plus the comment-key-value check against `view::extract(planned, &ancestor)` at each level (skipping already-covered subtrees). Simpler and preferred: reject in `parse_view` any `view_path` whose non-final segment is a comment key — a comment key is a leaf string by the document model, so nothing may legitimately live under one; this also closes the same hole for a `full_write` caller writing narrowly. Regressions: `?view=p.q__.r`, `?view=p.__.x`, `?view=p.a__.b.c` in both `replace` and `merge` must be 400 with no write; plus a property assertion beside the existing test that after any accepted scoped write, `model::lint(stored)` contains no finding absent before it.

### Q2 · medium · `ui/src/editor.rs:508` · S *(R3 residue; verifier split medium/low — adjudicated medium)*

**Defect.** R3 bundled two causes of one symptom; only the deleted-key half shipped. `self.access` — the other input `view_outcome`/`may_write`/`view_options` read — is fetched once per document: `need_access = self.access_for != Some(doc)` (editor.rs:508) is the sole read site, and `access_for` is written only in `create()` (:447), `changed()` (:485) and `Msg::Loaded`'s access branch (:620/627). Neither `Msg::Reload` (the toolbar's Refresh) nor `Msg::VersionToken`/`Msg::ServerDigest` (the 5 s poll) resets it or calls `api::access()` — the poll refreshes `self.keys` only. So when an admin revokes a scoped principal's grant while that principal's tab is open, `self.access.scopes` keeps the stale entry indefinitely: `view_options()` keeps listing the unauthorized prefix, `may_write()` keeps the Apply button enabled and the Read-only badge hidden, and `view_outcome()` keeps returning `Keep` because the stale scope alone satisfies its check. Because the revocation lives in `datacenter.yaml` while the open document is a guest document, the guest digest never changes, so no reload path fires either.

**Evidence.** Grep of `access_for`: three write sites, one read site, none in `Msg::Reload` or the poll handler; `api::access` has exactly one call site in the tree. Live on node1: after the admin drops the `traefik` entry from `datacenter.yaml`'s scopes map, the same token's `GET`/`PUT ?view=traefik` both 403 immediately — server enforcement is correct — while the client's poll (`api::get_text(doc,"")`) never errors, so nothing informs the UI. `cargo test --lib` green (`view_outcome()` is correct given its inputs; the defect is that a caller never updates one of them). `datacenter.yaml` restored byte-identical.

**Adjudication.** One verifier rated medium (mechanism confirmed, matches R3's own unshipped half), one low (server enforcement airtight, so no unauthorized read/write and no silent draft loss — Apply's 403 surfaces verbatim per DESIGN §6). Medium stands: the toolbar affirmatively misreports authorization state, and in the clean case the de-authorized view stays selected forever with no banner and no fallback — precisely the invariant R3 was raised to restore.

**Fix.** Reset `self.access_for = None` (or re-fetch `api::access(doc)` directly) in `Msg::Reload` and in the `VersionToken`/`ServerDigest` poll tick, feeding the result into `refresh_views()`/`view_outcome()` the way fresh `keys` already are. Regression: extend `meta-ui-r3-fix-check.js` (or a lib test) to revoke a *scope* rather than delete a key and assert the view drops from `view_options` and Apply disables within one poll interval.

### Q3 · medium · `docs/DESIGN.md:64` · S *(R8 residue)* — **verification INCOMPLETE: one of the two votes was a placeholder (`"test"`/`"test"`); this finding rests on a single substantive verification**

**Defect.** `docs/API.md:4` calls DESIGN §3 "the single source of truth for the API". R8 made the `access` handler route an orphan through `_orphan_or_404` and answer `{read, write, scopes: []}` computed purely from `Sys.Audit`/`Sys.Modify` on `/`. DESIGN §9's prose (lines 233-239) and the working tree's README row (line 70) state this; the §3 table row itself (line 64) still reads only "`{ read, write, scopes: [{prefix, mode}] }` for that document; without either, the caller's scopes and datacenter read/write", with no orphan case. This is the exact "P11 reconciled three rows, the fourth was never updated" pattern R9 fixed — recurring on the *access* row, introduced by R8 in the same pass-3 round and not re-checked. Other §3 rows already fold in this nuance inline (the guests row) or by cross-reference (`(§9)` on the guests/{vmid} row), so the omission is against the document's own convention.

### Q4 · medium · `docs/DESIGN.md:118` (+ `ui/README.md` Notes) · S *(R3 residue)*

**Defect.** The behaviour R3 fixed — when the selected view stops being an option (key deleted server-side, or the covering scope revoked), the editor falls back to the whole document, silently when clean and only after confirmation over unapplied edits (`ViewOutcome::{Keep,FallBack,ConfirmFallBack}` and `view_outcome()`, model.rs:156-179, consumed from `Msg::Loaded` ~:641 and `Msg::Reload` ~:807) — is documented nowhere. DESIGN §6 documents the toolbar, Apply's diff-confirmation dialog and the 409 notice at finer granularity than this; §8/§9 (binding) say nothing about it; `ui/README.md`'s Notes has "Unapplied edits are never thrown away without asking" for Reload and view-switch only. Grepping DESIGN.md, README.md and ui/README.md for fallback/ViewOutcome/selected view/vanished returns no description of the behaviour.

**Failure scenario.** Not a code defect — the mechanism is wired and unit-tested (model.rs:402-428) — but a documentation gap for data-loss-adjacent behaviour: an operator or integrator reading §6 cannot learn whether their unapplied edits survive a view disappearing under concurrent admin activity, or that a fallback happens at all.

**Fix.** Add a §6 bullet (binding-decision style): if the selected view stops being one of the caller's options — deleted, or the covering scope revoked — the editor falls back to the whole document, silently with a clean buffer and otherwise via the same confirmation dialog Discard/Reload/switch use. Mirror it in `ui/README.md`'s Notes beside the existing bullet, naming `ViewOutcome`/`view_outcome` as the source of truth.

## 5. Low findings checklist

- [ ] **Q5** `crates/pve-meta-core/src/store.rs:672` — the 4 MiB cap landed only in `read_document`; `version()` (the 5 s poll endpoint) does `digest::digest(&fs::read(path)?)` per file with no size check, and `digest_of` (store.rs:361) — called by `read_tolerant`'s `TooLarge` branch — is likewise uncapped, so listings and both write handlers still pull an oversized file fully into memory and hash it. SPEC's "the read cap bounds what an out-of-band file can cost on a path that runs per request" and store.rs:50-52 are false for the poll path. Separately the constant is unreachable in production (pmxcfs hard-caps `/etc/pve` files at 1 MiB), making every `TooLarge` read arm and `put_raw_gated`'s length guard dead code, api.rs:1640's premise included. Fix: skip or metadata-hash files above the cap in `version()`, give `digest_of` the same guard with an explicit contract, then either lower the constant to ~2× `MAX_BYTES` so the arms are reachable or document it as a backstop above pmxcfs's ceiling; add the end-to-end "an oversized file is not read by `version()`" test the pass-2 `MAX_BYTES` item and the pass-3 LOW both asked for.
- [ ] **Q6** `crates/pve-meta-core/src/api.rs:673` — R1's repair machinery keys on `parse_error` alone, but a file that *parses* to a non-map never sets it: `- 1` → array, a bare scalar → string, and an empty/whitespace/comment-only file → `Value::Null` (the most likely out-of-band corruption). Consequences: every narrow write including root's is refused by `descend`'s `blocked(&parent_path)` (view.rs:47), rendering for a top-level view as `400: invalid path: : a view prefix may only address into maps…` — an empty path naming nothing and no hint that a whole-document replace is the repair; `Document::parse_error`'s own doc comment (store.rs:128) and `read_or_empty`'s contract (api.rs:233) are both violated by `Null`; and `get_document` returns `data` as JSON `null`/array/string while `$VIEW_RETURNS` (Meta.pm:317) declares `data => { type => 'object' }`. Fix: widen the recoverability test from `parse_error.is_some()` to "the stored value is not an object", normalising to an empty map with a marker; make `blocked()` report the *requested* prefix; extend api.rs:1691 with the `null` root and assert on the message.
- [ ] **Q7** `crates/pve-meta-core/src/api.rs:494` — the `scopes` opaque-leaf rule is enforced for views, touched paths and scope prefixes but not for `list_guests`' `has` filter: `matches_has` calls `model::get_path(visible, path)` with a `DocPath::parse`d path that walks into the map, so `?has=scopes.k` matches while `?view=scopes.k` 400s on the same document. Fix: route `has` through `parse_view`'s check, assert it in `the_scopes_map_is_addressed_as_a_whole` (api.rs:1425), and add `has` to SPEC's list of addressing surfaces.
- [ ] **Q8** `crates/pve-meta-core/src/api.rs:951` — a root DELETE reports a wrong `touched` against SPEC.md:149-155's completeness invariant: for an unparseable document (newly reachable via R1) `stored.value` is the empty map, `patch::diff(&{},&{})` is empty, and the file is removed while the response says `touched: []`; for a non-map root, `view::remove` at root falls through `patch::diff_at`'s catch-all and answers `{path:"",op:"set"}` for a *delete*. ## 6. Before 1.0
