# pve-meta — adversarial review, adjudicated

## 1. Verdict

The design (DESIGN.md rev 4) is coherent; the implementation does not enforce it. The write-authorization boundary is the worst of it: `put_document` authorizes against the *realized diff* rather than the *requested path*, and `view::merge` mutates the document to create containers before the patch runs, so an empty-object merge creates arbitrary key structure at any path with `touched: []` and a vacuous `check_write` — reproduced live against a zero-ACL token on both a guest and the datacenter document, whose `scopes` map is itself the ACL config. The same diff-shaped check leaks document structure and confirms guessed leaf values through its 403 message. Around that, three classes of defect recur: invariants owned by two layers that disagree (digest checked in both `api.rs` and `store.rs`, so the documented create flow 409s; whole-document lint only inside `put_raw`, so `dry_run` accepts what the write rejects), validation deferred to read time (one malformed `scopes` entry, writable through the shipped editor, takes the whole guest API down cluster-wide for every principal including full-ACL admins), and unkeyed asynchrony (a view switch in the editor can silently write one view's text into another's path; whole-document digests make the 409 blind to it). Writes are unlocked read-modify-writes on a cluster-shared pmxcfs file with a non-node-unique temp name, contradicting the project's own PROXMOX-CONVENTIONS.md. Two documented behaviours are simply unreachable (`merge` + `null` deletes) or inverted (`replace` with `{}` deletes the key), the extension seam registers at BEGIN time so an extension path collision kills pvedaemon and pveproxy — inverting pve-ext's central promise — and roughly a fifth of `pve-meta-core` (the TOML format-preserving edit engine, `convert`, `clone`, `list_guests`, `make_patch`, the version cache) is unreachable from the shipped API while module docs advertise it as live.

## 2. Prioritized fix list

### G1 — Write authorization is computed from side effects, not from the request (fix as one change)

**F1 · critical · `crates/pve-meta-perl/src/api.rs:440` (and `:509`)**
`put_document`/`delete_document` mutate a working copy first, compute `touched` from the resulting diff, and gate solely on `Grants::check_write(&touched)`; `check_write([])` is vacuously `Ok`. A zero-grant caller therefore passes any write whose diff is empty, and `grants.can_write(&view_path)` is never called anywhere.
*Fix:* compute the mutation and its `touched` against a **clone**, run `check_write` on that plan, and only then apply to the value that reaches `store.put_raw`. Independently require `grants.can_write(&view_path)` up front; for a caller with no `full_write`, refuse a root-view write outright (require an explicit view inside a granted rw prefix). **M**

**F2 · critical · `crates/pve-meta-core/src/view.rs:189` (and `:198`)**
`merge`'s non-root branch calls `descend_creating(doc, &parent_path)` and `map.entry(key).or_insert_with(Object)` unconditionally *before* `patch::apply_obj`, so a no-op patch permanently creates the whole view-path skeleton while reporting `touched: []`. Verified live: `PUT ...?view=zzz_hacked.deep&mode=merge` with `{}` from a `traefik`-only token wrote `zzz_hacked: {deep: {}}` into a real guest document.
*Fix:* make container creation lazy inside the merge recursion (materialize a level only when a concrete key is about to be written under it), or splice a scratch subtree back into `doc` only when `touched` is non-empty. Add a regression test: `merge` must not mutate `doc` when it returns empty `touched`. **M**

**F3 · high · `crates/pve-meta-perl/src/api.rs:102-108` (`forbidden`)**
The 403 names the first offending path from a diff against real stored content, giving any authenticated principal a value-confirmation oracle and a full key-structure walk of any document (including `scopes`, i.e. every other principal's authid and prefixes) with no on-disk trace. Reproduced live.
*Fix:* return a generic "not permitted" when the caller has no read grant covering the path; keep the specific path only for callers with read access to its parent. Depends on F1 for the bulk of the closure. **S**

### G2 — Editor can write the wrong view, and destroys unsaved edits

**F4 · critical · `ui/src/editor.rs:367` (`Msg::Loaded`)**
`load()` captures `view` by value; the handler applies the result unconditionally with no check that `self.view`/`ctx.props().doc` still match, and `LoadableComponentMaster` respawns a load per `Msg::Load` with no cancellation. Because the digest is whole-document, the 409 check cannot detect it — live-reproduced writing view A's edited text into view B's path.
*Fix:* carry `(load_seq, doc, view)` through into `Msg::Loaded`; drop the message if any is stale (`return false`, do not touch `loaded`/`digest`/`generation`). Increment `load_seq` in `Msg::SelectView` and on a `doc` prop change. **S**

**F5 · high · `ui/src/editor.rs:551`, `:218`, `:406-418`**
The toolbar Reload, the stale-banner Reload, and `Msg::SelectView` all clear `self.draft` with no confirmation, while the adjacent Discard button is a `ConfirmButton` for the identical effect; `ui/README.md` states "Unapplied edits are never thrown away".
*Fix:* render Reload as a `ConfirmButton` when `draft.is_some()`. For `SelectView`, stash the pending view and route through the existing dialog machinery; on cancel leave `self.view` unchanged. Leave the stale-banner button as the sanctioned informed action (add a caption). **S**

### G3 — Extension seam can kill the management stack

**F6 · critical · `pve-ext/perl/PVE/API2/Ext.pm:285` (+ `pve-ext/patches/pve-manager_API2.pm.diff`)**
`use PVE::API2::Ext;` runs `_scan_and_register()` at BEGIN time, i.e. before *all seven* of PVE/API2.pm's own runtime `register_method` calls (lines 21-43, 51, 90). Extensions therefore register first, and the core registration that hits a duplicate path dies unguarded — `use PVE::API2` fails and both pvedaemon and pveproxy refuse to start. Latent today (only `ext_path = meta` ships).
*Fix:* change the diff to `require` + an explicit `PVE::API2::Ext->register_all();` placed at the very end of PVE/API2.pm; have `register_all` skip-and-warn on any `ext_path` already registered or in a reserved list (including `ext`), and fold Ext.pm's own currently-unguarded self-registration into it. **S**

### G4 — One malformed scopes entry is a cluster-wide outage

**F7 · critical · `crates/pve-meta-core/src/scopes.rs:124` + `perl/PVE/API2/Ext/Meta.pm:63`**
`parse_scopes` parses the whole map and fails on the first malformed entry; `scopes_for` calls it before extracting one authid. `_scopes_for` runs on every guest GET/PUT/DELETE, `/meta/guests` and `/meta/access`, for every caller. Nothing validates `scopes` on write — `model::lint` never inspects it — so an admin typo in the shipped editor 400s every guest read/write for everyone, including full-ACL admins, and the editor cannot load to fix it. Reproduced live (write via API, global 400, restore).
*Fix:* (a) run `parse_scopes` on the resulting datacenter document when a write touches `scopes` and reject 400 naming the entry; (b) add a lenient per-principal lookup that skips (and `warn!`s) malformed *other* entries so one bad entry can never deny service to unrelated principals — needed independently for entries already on disk; (c) have the editor's `load()` tolerate a 400 from `/meta/access`. **M**

### G5 — Documented merge/replace/comment semantics are wrong or unreachable

**F8 · critical · `crates/pve-meta-core/src/view.rs:303` (`view::parse`)**
`put_document` parses every payload through `view::parse` → `model::lint_relaxed`, which rejects `Value::Null` outright, before branching on mode. `merge`'s own (correct) `lint_patch` permits null but is dead code, so DESIGN §3's "`null` deletes" is unreachable through the API. Reproduced live in JSON and YAML, top-level and nested.
*Fix:* add `view::parse_patch(text, format)` running `patch::lint_patch`, and select it in `put_document` by `mode` before the single `payload_value` binding. Add an end-to-end test at the `put_document` layer. **S**

**F9 · high · `crates/pve-meta-core/src/view.rs:98` (`is_removal_marker`)**
`replace` treats a literal `{}` payload as a removal request, so a namespace whose value is legitimately `{}` cannot round-trip: opening that view in Monaco and clicking Apply with no edits deletes the key. Reproduced live against the installed daemon. Also contradicts `merge`'s own doc comment that empty and absent carry no distinction.
*Fix:* move the removal logic into `remove()` (which DELETE uses) and delete `is_removal_marker` from `replace`, so `mode=replace` with `{}` sets an empty map as DESIGN §3 says. Relocate the three tests that pin the old behaviour. **S**

**F10 · high · `crates/pve-meta-core/src/view.rs:277` (`filter_map`)**
Base keys are consumed with `include.remove(k)` while comment keys are tested with `include.contains_key(base)` in the same document-order pass, so `<key>__` is silently dropped from every scoped/partial read whenever it follows its own key — the natural authoring order. The existing test only covers the reverse order.
*Fix:* build a stable `HashSet<&str>` of included base keys before the pass (or use `get` and defer removal); add a regression test with `{"a":1,"a__":"c"}`. **S**

**F11 · medium · `crates/pve-meta-core/src/scopes.rs:74`**
Scope prefix `P` covers neither read nor write of the sibling comment key `P__`, while `view::filter` deliberately includes `P__` in an unscoped read — three inconsistent answers for one key, and no request a scoped principal can make ever writes the note about its own subtree.
*Fix:* in `can_read`/`can_write` (not in `Path::is_prefix_of`), treat a final segment `X__` as `X` when matching a same-depth prefix; state the rule in DESIGN §1/§2. **S**

### G6 — Two owners for one precondition; no lock on a cluster-shared file

**F12 · high · `perl/PVE/API2/Ext/Meta.pm:450` + `crates/pve-meta-core/src/store.rs:228`**
Every write is an unlocked read-modify-write of a whole document on `/etc/pve`; the repo contains no `cfs_lock_file`/`flock` anywhere, contradicting docs/design/PROXMOX-CONVENTIONS.md §5.6. Cross-node lost update observed live (both nodes 200, one change silently reverted). Separately, `write_atomic`'s temp name is `.{name}.tmp.{pid}` — not unique across nodes sharing one pmxcfs tree.
*Fix:* wrap the write handlers in `PVE::Cluster::cfs_lock_file("meta-$id", 10, sub {...})` (they are already `protected => 1`), doing read + digest check + write inside the critical section, and map lock timeout to a clean HTTP error. Make the temp name `hostname + pid + nonce`. **M**

**F13 · high · `crates/pve-meta-perl/src/api.rs:456` (and `:509`)**
`check_digest` at :438 accepts `Some("")` against a missing document (DESIGN §2), then the same digest is passed to `put_raw`, whose own guard rejects *any* `Some(_)` when no file exists — so the documented GET-then-PUT-with-digest create flow permanently 409s with "digest mismatch: expected , actual". The UI only escapes via a client-side special case.
*Fix:* keep `store.rs` as the single enforcement point (it must stay for the write-time recheck) and make its `None`-located branch treat `Some("")` as a match; render empty digests as `<empty>` in the error. Add a `put_raw(..., Some(""))`-on-missing test. **S**

**F14 · medium · `crates/pve-meta-perl/src/api.rs:452`**
`dry_run` skips `put_raw`, which is where whole-document `model::lint` actually runs; `view::replace`/`merge` only lint the subtree. Live: `?view=foo__&dry_run=1` → 200, same PUT without dry_run → 400 "comment key value must be a string".
*Fix:* call `model::lint(&value)` on the merged whole document once, before branching on `dry_run`. **S**

### G7 — Lifecycle patch tooling

**F15 · high · `pve-ext/bin/pve-ext-patch:374` (also `385`, `535`, `606`)**
No `--fuzz=0`, so GNU patch 2.8's default fuzz=2 applies. Reproduced with real file content: a one-line upstream drift made the `on_rollback` hunk jump 417 lines onto the byte-identical `__snapshot_commit` anchor and report success; `perl -c` passes and `status`'s reverse dry-run also reports "in sync". AbstractConfig.pm has four identical `lock_config($vmid, $updatefn)` lines and the docs call this disambiguation "load-bearing".
*Fix:* add `--fuzz=0` to all four invocations (verified to turn the case into a hard `Hunk FAILED`); treat a non-zero reported offset as a failure for the known near-duplicate-anchor files. **S**

**F16 · high · `pve-ext/bin/pve-ext-patch:375` (`apply_one` failure branches)**
On a re-apply after an upstream upgrade the diversion already exists, so `created_divert` is false and no failure branch touches `$real`: the live file keeps the **old patched** content while dpkg has installed the new pristine at the diverted path and updated every other file in the package. postinst swallows this with an `echo` to stderr. Worse, `status_one`'s in-sync check reverse-applies the same diff against that stale file and reports "in sync: yes" (only `verify` catches it).
*Fix:* on any failure where the diversion pre-existed, `cp -a "$diverted" "$real"` so the node runs a consistent, unhooked, current file; fall back to leaving `$real` alone if that copy fails. Fix `status_one` to compare the live file against a freshly rendered `$diverted + diff` candidate. Surface the failure via a marker file/syslog, not just stderr. **M**

**F17 · high · `scripts/watch-pve/check.sh:31-32`**
`LIFECYCLE_DIR` and `UI_PATCH_TOOL` point at `pve-manager-patches/lifecycle/` and `pve-manager-patch/pve-meta-patch`, neither of which exists. Result: lifecycle checks silently pass ("nothing to dry-run") having tested nothing, and `check_pve_manager` fails with "No such file or directory" on every pve-manager bump, opening a `pve-upgrade` issue blaming a patch failure that was never tested.
*Fix:* `LIFECYCLE_DIR="$REPO_ROOT/patches/lifecycle"`; replace the tool call with `pve-ext/bin/pve-ext-patch --root "$extracted" verify pve-manager`. Optionally drive the lifecycle check through `patches/lifecycle.toml` the same way. Update the stale comments in check.sh, ceilings.toml and docs/DISTRIBUTION.md §6. **S**

**F18 · medium · `pve-ext/bin/pve-ext-patch:367`** *(overruled refutation — see §4)*
A second manifest naming a path a first manifest already patched seeds its scratch copy from the shared pristine diversion, silently discarding the first manifest's hunks; `remove_one` undiverts a path other manifests may still need, and `verify`/`status` inherit the one-diff-at-a-time assumption.
*Fix:* record which manifest(s) claim each diverted path (a small state file next to the diversion) and make `apply_one` fail loudly when a second manifest claims an already-claimed path; make `remove_one` refuse to undivert while another claim remains. Document the limitation in pve-ext/README.md meanwhile. **M**

### G8 — Destructive reach-through and unbounded creation

**F19 · high · `crates/pve-meta-core/src/store.rs:461`**
`MetaStore::delete` cascades into `list_snapshots`/`delete_snapshot`, and `api::delete_document` calls it for a root-view DELETE — an endpoint whose API surface has no concept of snapshots. Because `on_rollback` reads a missing snapshot copy as `RemovedNoSnapshot` and *deletes the live document*, the loss propagates forward: reproduced live (DELETE ate `999000.snapA.yaml` unmentioned; a later `on_rollback` silently deleted freshly rewritten metadata). Note `destroy()` is currently just an alias for `delete()`.
*Fix:* give `delete()` a non-cascading body (live document only) and move the cascade into `destroy()`, used solely by `on_destroy`. Tests: bare `delete` leaves snapshots; `destroy` removes them; an api-delete-then-rollback end-to-end case. **S**

**F20 · high · `perl/PVE/API2/Ext/Meta.pm:448` (and `delete_guest`)**
Nothing consults the vmlist on write, so "every guest document" is implemented as "every u32": a zero-ACL token with one rw scope can create unbounded files under `/etc/pve/meta` (pmxcfs replicates them cluster-wide and has a hard size budget), invisible to `GET /meta/guests`, and a later real guest at that vmid silently inherits the metadata. Reproduced live.
*Fix:* look the vmid up in `PVE::Cluster::get_vmlist()` in `put_guest`/`delete_guest` before the Rust call and 404 if absent (all callers, not just scope-only); leave `get_guest` as-is. Add an orphan sweep for documents whose vmid left the vmlist. **S**

### G9 — Read-side disclosure and UI grant mismatch

**F21 · medium · `perl/PVE/API2/Ext/Meta.pm:494` / `crates/pve-meta-perl/src/api.rs:368-377`**
A view-less GET treats "no grants" as "empty union": a caller with no access gets 200, `data: {}`, and the document's **real** digest — contradicting `get_datacenter`'s own registered "Requires Sys.Audit on /" and turning the digest into a change-detection oracle over the `scopes` map. Reproduced live (identical digest to root's full read).
*Fix:* 403 when `readable_prefixes()` is empty (for the datacenter endpoint: whenever `full_read` is false, since scopes never apply there). Do **not** blank the digest for non-empty partial reads — scoped writers need the whole-document digest for compare-and-swap PUTs. Write the no-grant case into DESIGN §3. **S**

**F22 · medium · `ui/src/model.rs:161` + `perl/PVE/API2/Ext/Meta.pm:305-324`**
`/meta/access` computes `full` from audit privileges only (Sys.Audit / VM.Audit); the UI uses that same field as the write grant, so a Sys.Audit-only auditor gets an editable Monaco buffer and an enabled Apply, learning otherwise only from a 403 after confirming the diff. `Meta.pm` already computes `full_write` correctly elsewhere (`_grants_json`) — it just isn't exposed here.
*Fix:* return `full: { read: '*'|[vmids], write: '*'|[vmids] }` built from `Sys.Modify` / `VM.Config.Options`; split `FullAccess` in the UI so `may_write` consults the write half; update DESIGN §3 and the `full_access_writes_everything` test. **M**

**F23 · medium · `perl/PVE/API2/Ext/Meta.pm:120` (`_inflate_view`)**
`decode_json` into a plain Perl hash destroys document key order for every `format=json` read (Perl hash randomisation; verified — order varies call to call while `format=yaml` is stable), defeating the ordered-map invariant `preserve_order` exists to uphold. The editor's "View as" list is built from this path, so it reorders between page loads.
*Fix:* point the UI's key list at an ordered `keys` array (already order-preserving on `GET /meta/guests`; add the same field to the single-document GET), and state in DESIGN §3 that `format=json`'s `data` object is unordered. **M**

### G10 — Dead subsystems and misleading module docs

**F24 · medium · `crates/pve-meta-core/src/edit.rs:37` + `store.rs:293/426/613/471`, `patch.rs:191`**
`MetaStore::patch` (the only caller of `edit::apply_patch_text` and of `toml_edit`), `convert`, `clone`, `list_guests`/`GuestEntry` and `make_patch` have no production caller; every real write goes `view op → format::dump → put_raw`, and `dump_toml` rebuilds from scratch. `edit.rs`'s doc comment promises TOML comment/formatting preservation that no API write can ever perform, and `settings.default_format: toml` (F26) is a reachable way to get TOML files that then lose their formatting on the first edit.
*Fix:* delete the unreachable surface and the `toml_edit` dependency, and correct `edit.rs` / `lib.rs` module docs, `format::dump`'s docs and DESIGN §7's TOML note to say TOML is rewritten canonically — or wire `MetaStore::patch` into `put_document` for `mode=merge` on TOML-backed documents. **M**

**F25 · medium · `crates/pve-meta-core/src/store.rs:700`**
`open_store()` builds a fresh `MetaStore` per request, so the per-file digest cache is always empty on lookup — write-only, with a carefully-argued 2s staleness rule that can never apply, while every `/meta/version` poll rescans and re-hashes the store. Separately, the cache is unsound when it *does* apply: `(mtime, len)` cannot distinguish two same-length writes in one pmxcfs mtime tick (reproduced; 50 back-to-back writes on-node all shared one mtime), so a primed entry can serve a stale digest. Blast radius is the poll token only — the PUT 409 check always re-hashes.
*Fix:* delete the cache and always re-hash (the doc comment already concedes files are tiny), or give the bindings a process-lifetime store keyed on the resolved root **and** replace the `(mtime,len)` key with a write-sequence tag. Do not adopt the "record insertion wall-clock" variant — it does not fix the collision. **S**

### G11 — Under-specified knobs

**F26 · medium · `crates/pve-meta-core/src/store.rs:642`**
`settings.default_format` is an undocumented, unvalidated magic key inside the user-owned free-form datacenter document (DESIGN reserves only `scopes`) that silently controls the on-disk format of every newly created document, and is the only way to reach TOML at all since the wire API rejects `format=toml`. Reproduced live: writing `settings: {default_format: json, owner: ops}` made the next new guest document `999006.json`.
*Fix:* always create new documents as YAML and drop the key (existing `.toml`/`.json` files keep working via `locate_stem`), or move it out of the user's namespace and document + validate it like `scopes`. **S**

## 3. Cross-cutting themes

**Authorization derived from effects rather than from the request.** F1/F2/F3 are one bug wearing three faces: the security boundary sits *after* the mutation, reading a diff the mutation itself under-reports. `Meta.pm` registers every write handler as `permissions => { user => 'all' }`, so `check_write(&touched)` is the *entire* gate by explicit design — which makes any under-reporting of `touched` a total bypass, and makes the 403's diagnostic detail an oracle. Any code that decides permission from a value it has already changed is structurally wrong here.

**One invariant, two owners, two rules.** The digest precondition lives in both `api.rs` and `store.rs` and they disagree about `Some("")` (F13). Whole-document lint lives only inside `put_raw`, so `dry_run` — whose whole job is to stand in for the write — validates strictly less (F14). Delete-with-snapshot-cascade is shared by the REST API and the lifecycle destroy hook via one function (F19). Each of these is cheap to fix once, and each will recur wherever a second layer re-derives a rule.

**Validation is read-time, not write-time.** `scopes` is a structure the design specifies precisely, written through a generic free-form document path that never checks it, and parsed all-or-nothing on every request (F7). The same shape appears in F26 (`settings.default_format` is behaviour-controlling config living in user data with no validation). Structured meaning inside a free-form tree needs a write-time gate and a fail-soft reader.

**Order- and context-dependence.** `filter_map` consumes the map it is iterating (F10); the editor applies async responses with no request identity (F4); `pve-ext-patch` relies on context uniqueness while letting GNU patch discard context (F15); `PVE::API2::Ext` registers at BEGIN and therefore always wins an ordering race it should always lose (F6). Four different subsystems, one missing discipline: name the thing you are matching against, and check it at the point of use.

**The design doc under-specifies exactly where the code improvises.** `{}` in replace (F9), comment keys under scopes (F11), no-grant reads (F21), read-vs-write in `/meta/access` (F22), key order across the Perl boundary (F23). Each is a corner DESIGN.md states loosely and the implementation resolved silently and inconsistently. These want a decision written down, not just a patch.

**Leftovers from revision 4 were never swept.** A format-preserving TOML edit engine, `convert`, `clone`, `list_guests`, `make_patch` and a version cache that cannot hit (F24, F25) remain, advertised as live in `lib.rs`'s module map and SPEC.md; five documents still describe the pre-`pve-ext` architecture (F30); the ceiling-watcher CI script points at that dead layout and consequently tests nothing while failing loudly (F17). The rewrite changed the code and left the map.
