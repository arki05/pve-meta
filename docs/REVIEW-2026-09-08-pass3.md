# pve-meta — adversarial review, pass 3 (targeted, adjudicated)

## 1. Verdict

Pass 2 found a security boundary correct about paths and blind about actors, plus a read path that turned any out-of-band typo into a cluster-wide outage: 2 critical, 4 high, 7 medium, 18 low. Nine of the thirteen numbered findings are now fixed and independently verified — the `scopes` actor gate (P1), the lenient `scopes_for` container (P3), the bare-`__` read/write agreement (P4), authid-shaped scope keys with `scopes` as an opaque leaf (P9), `--root` isolation of the failure marker (P6), manifest-declared claim identity (P7), the Reload invalidation (P8), the conventions-doc sweep (P12) and lintian in both `deb:` targets (P13) — with essentially the whole pass-2 low checklist closed, several beyond remit. Four are partial (P2, P5, P10, P11), and the shape of what remains has changed: pass 3 is 1 critical, 4 high, 4 medium, 7 low, and **two of the nine confirmed findings were introduced by pass-2 fixes rather than left behind by them**. The critical is P2's unfinished half: moving `model::lint` off the read path fixed the lint case and left the *parse* case untouched, so a hand-edit indentation slip, a tab or a YAML anchor in `datacenter.yaml` still 400s every endpoint cluster-wide for every principal including root, and — worse than the lint case pass 2 described — root can neither `GET`, `PUT` nor `DELETE` the document to repair it. The same fix made `store.read` return unlinted content, which uncovered `view::filter`'s never-reachable fallback arm: a document whose on-disk top level is a list or a scalar is now handed in full to a scope-only reader. On the packaging side, the `--root` failure-injection testing pass 2 asked for exposed that `restore_on_failure` never actually undoes a fresh diversion and that five of `apply_one`'s eleven failure exits leave no durable trail at all — both in the exact functions P6/P7 rewrote. The remaining residue is P5's and P11's second halves, again the pass-2 pattern: the remit was split and only the named half shipped.

## 3. Prioritized fix list (confirmed)

### R1 · critical · `crates/pve-meta-core/src/store.rs:235` (and `:322`, `api.rs:201`) · S
**Defect.** P2's fix removed `model::lint` from the read path but left `format::parse_raw`'s *syntax* layer fatal. `scan_yaml_safety` + `serde_yaml_ng` reject anchors/aliases, explicit tags, complex keys, tabs and indentation slips with `Error::Parse`, which `read_document` propagates with `?`. `api::grants` reads `DocId::Datacenter` on every request and Perl's `_scopes_for` runs on every guest GET/PUT/DELETE, `/meta/guests`, `/meta/access` and `/meta/datacenter`, so one malformed `datacenter.yaml` is a cluster-wide 400 for every principal, root included. Repair is impossible through the API: `put_document` and `delete_document` both call `read_or_empty` (api.rs:201) *before* planning, so a root-level `replace` and `DELETE /meta/datacenter` fail with the same error — the outer guard fires before `put_raw`'s lenient old-bytes parse is ever reached. `GET /meta/version` is the only surviving endpoint. Live-reproduced four ways on node1 (anchor, merge key, tab, bad indent), document restored byte-identical. Contradicts DESIGN §9's "reads never lint. The store reads and returns what is on disk" and leaves P2's stated remit ("a full-ACL admin cannot GET the document to see what to fix, and cannot repair it") unmet.
**Fix.** Treat unparseable stored content as *replaceable*, not fatal, in the same two places P2 already treated for lint. (a) In `read_or_empty` (api.rs:201) and `grants` (api.rs:315), map `CoreError::Parse{..}` the way `NotFound` is mapped — empty document plus the *real* on-disk digest, so `put_document`/`delete_document` can still enforce their precondition. (b) In `put_raw` (store.rs:318-323), fall back to an empty `Value::Object` when the old bytes do not parse. Keep store.rs:330's strict `format::parse` of the new text as the sole write gate; let `get_document` return the raw text for `format=yaml` (or a read-only 400 saying "the stored document is not valid YAML"). Regression tests at API level, not just `store::read`: with a `datacenter.yaml` containing an anchor / a tab / a bad indent, `grants` returns `[]`, an unrelated guest GET/PUT works, and a root-view `replace` and `DELETE /meta/datacenter` both succeed.

### R2 · high · `crates/pve-meta-core/src/view.rs:312` · S *(regression introduced by the P2 fix)*
**Defect.** `filter`'s catch-all arm returns `other.clone()` for any non-object document, never consulting `readable_prefixes`. The root-prefix early return at :307 only fires for `full_read`, so a scope-only caller reaching this arm gets the whole file. Before P2 this arm was unreachable — `store.read` linted, and lint rule 1 ("top level must be an object") turned such a document into a 400. Now `get_document`'s view-less branch (api.rs:452) returns it verbatim, and `list_guests`' `matches_has` (api.rs:341) makes `?has=` a content oracle over the same value. Reproduced live on node1 with a zero-ACL scoped token against a document rewritten out-of-band as a list and as a bare scalar, and again in-crate. The function's own doc comment (view.rs:298-305) claims it emits only what the prefixes cover; there is no test for a non-object root.
**Fix.** `other => Value::Object(Map::new())` at view.rs:312. Add `filter(&json!([1,2,3]), &[p("a")]) == json!({})` and the scalar case beside `filter_never_emits_a_bare_map_comment_the_grant_cannot_read`, keep `filter(&json!([1,2,3]), &[Path::root()])` returning the array for a full-read caller, and add an api-level test that a scope-only grant gets no content (403 / empty) for a sequence-rooted document through both the view-less GET and `?has=`.

### R3 · high · `ui/src/editor.rs:592` (with `:529`, `:488`) · M *(regression introduced by the P10 fix)*
**Defect.** P10 folded the key list into the single document GET, so `self.keys` is refreshed only when the answered view is empty (`view.is_empty().then(|| document_keys(&document))`), and `self.access` only when the document changes (`need_access = self.access_for != Some(doc)`). `RequestTracker` governs which answer is accepted, not what is requested, so a reload issued while a non-empty view is selected keeps asking for that view. The "selected prefix is gone — fall back to the whole document" check at :589-595 is computed from `self.access.view_options(&self.keys)`, i.e. the stale state, so when the viewed key is deleted server-side (or its scope revoked), the 5 s version poll's auto-reload returns an empty subtree, `options.contains(&id.view)` is still true, and the fallback never fires. Live-reproduced on node1 (guest 200, view `traefik` deleted externally, 9 s wait): selector still `traefik`, buffer `{}\n`, "View as" still lists `traefik`; document restored byte-identical. Applying an edit into that buffer sends `PUT ?view=traefik&mode=replace`, silently resurrecting the deleted key — or, in the revoked-scope case, hitting a 403 the toolbar gave no reason to expect.
**Fix.** Treat a non-empty view whose answer is exactly the empty-map sentinel as ambiguous and re-validate against a fresh whole-document `keys`+`access` fetch before accepting "still exists, just empty". Refresh `self.access` per reload (or at least on every poll-triggered reload) rather than per document, since a revoked scope is the same bug on the grants side of the same check. Regression: reproduce the deletion path in the headless harness and assert the fallback to the whole document.

### R4 · high · `pve-ext/bin/pve-ext-patch:417` · S
**Defect.** `restore_on_failure`'s `created_divert=1` branch calls `dpkg_divert_remove "$mpath" >/dev/null 2>&1` with the exit status discarded, then unconditionally logs "rolling back diversion created moments ago" and deletes the claim marker. But `apply_one`'s placeholder-restore step (:550-557) has already copied the pristine backup onto `$real`, and `dpkg-divert --remove --rename` refuses to rename onto an existing regular file — the tool's *own* `remove_one` (:658-661) documents this restriction and does `rm -f "$real"` first. So every failure return after the placeholder restore (patch dry-run, patch apply, `perl -c`/template check) leaves the diversion live in dpkg's database, owned by `pve-ext`, with the claim marker deleted and the log asserting a rollback that did not happen. Reproduced twice under `--root` on the build host with the real host verified untouched: after apply, `dpkg-divert --root … --list` still shows the diversion and `status` reports APPLIED / "claimed by: `<none recorded>`". Contradicts the function's own header comment for the one branch not documented as best-effort. The next upgrade of the file's owning package then installs to the diverted `.pve-ext-orig` path while `$real` keeps the untracked stale placeholder — the exact staleness the sibling branch guards against.
**Fix.** `rm -f "$real"` before `dpkg_divert_remove`, check its exit status, and delete the claim marker / log success only on success; otherwise `record_failure` and `err` with the true state.

### R5 · high · `pve-ext/bin/pve-ext-patch:390` (call sites `:505`, `:511`, `:524`, `:529`, `:560`) · S
**Defect.** P6 root-isolated `record_failure`'s writes, but five of `apply_one`'s eleven failure returns never call it: "diff not found", "diverted by a DIFFERENT package", "expected file not found" (the "anchors moved upstream" case the tool's own comments call normal), "dpkg-divert --add failed" and "mkdir scratch dir failed". `cmd_apply` only does `|| rc=1` and never compensates; there is no `set -e`. The only trace is stdout/stderr at invocation — precisely what `record_failure`'s header comment (:370-378) and `pve-ext-patch.8`'s FILES section say the marker exists to survive, since `debian/pve-meta.postinst` swallows apply's exit code by design. Reproduced under `--root` for the absent-target and foreign-diversion branches (and incidentally for the divert-add branch): `<root>/run/pve-ext-patch/failed` is never created.
**Fix.** Call `record_failure "$mpath" "<message>"` immediately before each of the five bare `return 1`s, matching the six branches that already do.

### R6 · medium · `crates/pve-meta-core/src/api.rs:514` · S *(P2 residue; one verifier rated high, adjudicated medium — the disclosure requires an already out-of-band-corrupt document)*
**Defect.** `plan_write` runs `model::lint(planned)` over the whole document and renders every finding verbatim into the 400 (`error.rs:27-28` joins absolute paths with no read filter). Two consequences. (1) Disclosure: a principal whose only grant is one prefix learns the existence and exact spelling of keys in subtrees they cannot read — `forbidden()` (api.rs:129) applies exactly this filter for 403s per DESIGN §8, and the 400 path does not. Live: `scoped@pve!t1` reading guest 201 sees only `traefik`, but `PUT ?view=traefik` returns `400 … secret_area.customer name: invalid key …`. (2) Availability: one out-of-band bad key anywhere blocks every write by anyone who cannot write the root view, since a root replace is the only repair shape. DESIGN §9's "strict lint runs only on the content being written" is not what this code does.
**Fix.** Keep the full lint as the decision, but partition `lints` by `grants.can_read(&lint.path.parent())` before rendering — share one predicate with `forbidden()` — reporting readable findings verbatim and collapsing the rest into one path-free sentence. Regression: the scoped writer's 400 contains neither `secret_area` nor `customer name`; a `full_read` caller still gets the full message. Follow-up (separable): scope the write gate to the touched subtrees plus the payload so an unrelated out-of-band key denies nobody.

### R7 · medium · `crates/pve-meta-core/src/patch.rs:125` · S
**Defect.** `apply_obj`'s catch-all arm inserts the patch value verbatim when the target key is absent or non-object, so nested `null` delete markers are spliced into the document as literal nulls; `plan_write`'s lint then rejects the result with "null values are not allowed". `lint_patch_at` deliberately accepts those nulls, and DESIGN §3/§8 document `null` as the merge delete marker and "a merge that touches nothing changes nothing". `view::merge` already does the empty-scratch trick for the top-level view key; it was never threaded through `apply_obj`'s recursive fallback. Reproduced both by calling `view::merge` directly and end-to-end through `api::put_document`: `{"sub":{"gone":null}}` into an absent `sub`, `{"a":{"deep":null}}` over a scalar `a`, and the root-level `{"nope":{"gone":null}}` all 400. Flat forms behave correctly. Fails closed — nothing is persisted — so no corruption, but the documented combined set+delete patch shape is unusable against a not-yet-existing container.
**Fix.** In the `_` arm, when the patch value is an object, replace the target with an empty object and recurse via `apply_obj` with the same child path; push a `Touched{Set}` for the container only if the recursion actually touches something. Tests: absent container + nested null is a no-op with no touched entries; `{"a":{"x":1,"y":null}}` over a scalar `a` yields `a: {x: 1}`; nothing accepted by `lint_patch_at` can trip the whole-document lint.

### R8 · medium · `perl/PVE/API2/Ext/Meta.pm:441` · S *(P5 residue)*
**Defect.** P5 made orphans first-class in `list_guests`, `get_guest` and `delete_guest`, but the `access` handler still calls the unconditional `_assert_guest_exists($vmid)` it inherited by copy-paste from `put_guest`, so it 404s for a vmid the same caller can list, GET and DELETE. Four handlers, three orphan models.
**Fix.** Replace `_assert_guest_exists($vmid)` with `_orphan_or_404($rpcenv, $authuser, $vmid)`; when it reports an orphan, answer from `_guest_grants_json`'s existing `$orphan` branch (`Sys.Audit`/`Sys.Modify` on `/`, empty `scopes`). Add a regression case beside the existing orphan tests and one sentence to DESIGN §9's orphan bullet stating what `/meta/access` returns for an orphan vmid.

## 6. Before 1.0

What is solid: the authorization boundary. P1 closed the actor hole with an explicit `full_write` gate plus two parse-time prefix rules, verified live from both directions; P4 made read and write agree on comment keys at every position tested, with the pinning tests replaced by invariant tests rather than deleted; P9 gave `scopes` an authid-shaped key rule and opaque-leaf addressing without leaking another principal's authid into a 403. The `pve-ext` seam's two identity defects are genuinely fixed — claim identity now comes from the manifest itself and `--root` no longer writes to the real host, both confirmed by failure injection against snapshotted host state. Packaging is in good shape: lintian runs in both `deb:` targets with zero `E:` on the real artifacts, the version cross-check and the man page landed, and the whole pass-2 low checklist except three items is closed, several beyond remit. The UI's request-fencing story is complete (P8 wired `invalidate()`, the dead tracker surface is gone rather than merely used), and the two behaviours this pass was asked to check directly — whole-document read denial and the empty-document load — both behave correctly live.

What to do before 1.0. Three things, in order. First, **finish P2**: R1 is the one critical, and it is the same defect pass 2 filed, with the same blast radius, reached through the parse layer instead of the lint layer — a hand-edit typo in `datacenter.yaml` still takes the whole API down for everyone with no API repair path. Ship it together with R6 (same document, same lint/disclosure axis) and R2, which exists only because the P2 fix made unlinted content reachable and nobody re-audited the readers that had relied on lint as a precondition. That is the general lesson of this pass: **two of nine confirmed findings were created by pass-2 fixes** (R2 by P2, R3 by P10), both because a fix removed a validation or a fetch that another layer silently depended on. Any remaining fix should carry an explicit list of the invariants it stops providing. Second, **close the partials properly this time**: P5's and P11's remaining halves (R8, R9, plus the orphan-ACL LOW) are the identical "only the named half shipped, no marker left behind" pattern pass 2's own §6 called out, now on its second round — the orphan model is currently implemented three different ways across four handlers. Third, **re-test `pve-ext-patch`'s failure paths, not just its success paths**: R4 and R5 both sat inside functions the pass-2 fixes rewrote and were only found by injecting failures under `--root`. Until they are fixed, the tool's durable failure trail — the thing `postinst`'s swallowed exit code depends on — does not exist for five of eleven failure modes, and its rollback both fails and reports success. R3 and R7 are smaller but should not ship as known-broken: R3 can silently resurrect deleted content on a routine Apply, and R7 makes a documented merge shape unusable.
